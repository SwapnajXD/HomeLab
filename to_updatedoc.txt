# Apollo Networking Incident & Recovery Report

**Date:** 2026-06-02
**Host:** Apollo (Proxmox VE)
**VM:** Athena (VMID 100)
**LXC:** Hestia (CTID 101)

---

# Overview

The goal was to provide internet access to the Alpine LXC container **Hestia** while keeping the setup simple and avoiding Tailscale/TUN passthrough inside the container.

During troubleshooting, multiple networking issues were discovered:

1. Hestia could not obtain a DHCP lease.
2. The container had no IPv4 address.
3. NAT was not functioning correctly.
4. Apollo's networking configuration contained stale and conflicting bridge definitions.
5. Proxmox firewall bridges were interfering with connectivity.
6. Athena VM was still attached through a Proxmox firewall bridge.

All issues were eventually resolved.

---

# Issue #1: Hestia Had No IPv4 Address

## Evidence

Container interface:

```bash
pct exec 101 -- ip addr
```

Output:

```text
eth0@if38
inet6 fe80::...
```

No IPv4 address existed.

---

## Root Cause

Container configuration:

```text
net0:
  bridge=vmbr0
  ip=dhcp
```

But vmbr0 was configured as:

```text
bridge-ports none
```

There was no DHCP server connected to the bridge.

Therefore:

```text
Hestia -> DHCP Discover
Nobody replies
No IP assigned
```

---

# Issue #2: DHCP Failed

## Evidence

Inside Hestia:

```bash
udhcpc -i eth0
```

Output:

```text
broadcasting discover
broadcasting discover
broadcasting discover

failed to get a DHCP lease
```

---

## Root Cause

No DHCP service existed on vmbr0.

---

# Fix

Switched to static addressing.

Container network configuration changed from:

```text
ip=dhcp
```

to:

```text
ip=10.10.10.2/24
gw=10.10.10.1
```

Final configuration:

```text
net0: name=eth0,bridge=vmbr0,firewall=0,gw=10.10.10.1,ip=10.10.10.2/24,type=veth
```

---

# Issue #3: NAT Not Working

After assigning:

```bash
ip addr add 10.10.10.2/24 dev eth0
ip route add default via 10.10.10.1
```

Container could reach Apollo:

```bash
ping 10.10.10.1
```

Success.

But:

```bash
ping 1.1.1.1
```

Failed.

---

## Root Cause

Apollo was not masquerading container traffic to the WiFi interface.

---

# Fix

Enabled forwarding:

```bash
echo 1 > /proc/sys/net/ipv4/ip_forward
```

Added NAT:

```bash
iptables -t nat -A POSTROUTING \
  -s 10.10.10.0/24 \
  -o wlx002e2df0393b \
  -j MASQUERADE
```

Added forwarding rules:

```bash
iptables -A FORWARD \
  -i vmbr0 \
  -o wlx002e2df0393b \
  -j ACCEPT

iptables -A FORWARD \
  -i wlx002e2df0393b \
  -o vmbr0 \
  -m state --state RELATED,ESTABLISHED \
  -j ACCEPT
```

Result:

```bash
ping 1.1.1.1
```

Succeeded.

# Issue #4: Apollo Network Outage

During editing of:

```text
/etc/network/interfaces
```

Apollo became unreachable.

Lost:

* SSH
* Tailscale
* Proxmox UI

---

## Root Cause

NetworkManager manages the WiFi interface.

The file contained conflicting configuration:

```text
auto wlx002e2df0393b
iface wlx002e2df0392b inet static
```

Notice:

```text
0393b
0392b
```

Different interface names.

Additionally:

```text
192.168.1.150
```

was configured while NetworkManager was actively assigning:

```text
192.168.1.20
```

This created conflicting management.

---

# Recovery

Used physical console access.

Verified NetworkManager:

```bash
nmcli device status
```

Confirmed WiFi was connected.

Allowed NetworkManager to continue managing WiFi.

No further changes made to WiFi configuration.

---

# Issue #5: Proxmox Firewall Bridge Interference

Even after fixing IPs, Hestia could not reach vmbr0.

Bridge inspection:

```bash
brctl show
```

Showed:

```text
fwbr101i0
fwln101i0
fwpr101p0
```

Instead of:

```text
vmbr0
```

Container traffic was passing through firewall bridges.

---

## Root Cause

Container configuration contained:

```text
firewall=1
```

Previously enabled firewall networking.

---

# Fix

Disabled firewall networking.

```bash
pct stop 101
```

```bash
pct set 101 \
-net0 name=eth0,bridge=vmbr0,firewall=0,gw=10.10.10.1,ip=10.10.10.2/24
```

Stopped firewall service:

```bash
systemctl stop pve-firewall
```

Started container:

```bash
pct start 101
```

Verification:

```bash
bridge link | grep 101
```

Output:

```text
veth101i0 master vmbr0
```

Container attached directly to vmbr0.

Connectivity restored.

---

# Issue #6: Athena VM Was Also Using Firewall Bridges

VM configuration:

```text
net0:
  bridge=vmbr0
  firewall=1
```

Bridge inspection showed:

```text
tap100i0 -> fwbr100i0
```

instead of vmbr0.

---

# Fix

Disabled VM firewall networking.

```bash
qm set 100 \
--net0 virtio=BC:24:11:43:4C:5F,bridge=vmbr0,firewall=0
```

Restarted VM:

```bash
qm stop 100
qm start 100
```

Verification:

```bash
bridge link | grep 100
```

Output:

```text
tap100i0 master vmbr0
```

VM attached directly to vmbr0.

# Issue #7: Stale vmbr1 Bridge

Discovered:

```bash
ip addr show vmbr1
```

Output:

```text
vmbr1
10.10.10.1/24
```

Yet:

```bash
grep vmbr1 /etc/network/interfaces
```

returned nothing.

And:

```bash
grep -R vmbr1 /etc/pve
```

returned nothing.

---

## Root Cause

Old bridge remained in kernel memory from previous experiments.

No configuration referenced it.

---

## Verification

```bash
brctl show vmbr1
```

Output:

```text
vmbr1
(no interfaces attached)
```

---

## Fix

Removed manually:

```bash
ip link set vmbr1 down
ip link delete vmbr1 type bridge
```

# Lessons Learned

1. **Never use DHCP on a bridge without a DHCP server.**
2. **Always verify bridge membership with `brctl show` and `bridge link`.**
3. **Proxmox firewall networking inserts additional bridge layers (`fwbr*`) that complicate troubleshooting.**
4. **When using WiFi, avoid mixing NetworkManager and manual interface configuration unless absolutely necessary.**
5. **Always keep physical console access available before modifying host networking.**
6. **For simple homelab setups, direct attachment to `vmbr0` with static addressing is much easier than Tailscale passthrough or nested VPN networking.**

## 🛠️ Summary of Actions & Architecture Changes

### 1. Migrated & Segregated the Workloads

We broke up your monolithic architecture and distributed your workloads into a secure, logical tier system across two distinct environments:

* **Hestia (`10.10.10.2` - LXC Container):** Designated as your **Personal/Core Tier**. We migrated **Homepage** and **Vaultwarden** here to keep your daily utilities isolated, stable, and highly responsive.
* **Athena (`10.10.10.10` - Ubuntu VM):** Designated as your **Dev/Monitoring Tier**. This hosts **Portainer**, your complete telemetry stack (**Grafana, Prometheus, Loki, Promtail, Node Exporter**), and your local cloud sandbox (**LocalStack**).

### 2. Streamlined the Network Topology

Instead of enabling full Tailscale subnet routing (which would have exposed your entire local home subnet to the mesh), we implemented a **Strict Port-Forwarding Translation Layer** on your primary node, **Apollo (`100.81.86.51`)**.
Apollo handles the incoming secure Tailscale connections from your laptop (`Artemis`) and surgically targets individual ports using `iptables`, bouncing them down to the internal Proxmox private network bridge (`vmbr0`).

## 🛑 Roadblocks Faced & How We Solved Them

### 💥 Roadblock 1: Port Collisions on `3000`

* **What Happened:** Homepage and Grafana both natively want to bind to port `3000`. Moving Homepage to Hestia while leaving Grafana on Athena meant they were on different IPs, but our entry-point routing via Apollo's Tailscale IP caused a direct conflict.
* **How We Solved It:** We rewrote the network interfaces rules on Apollo to assign **Grafana to custom port `3001**`, leaving `3000` cleanly dedicated to Homepage.

### 💥 Roadblock 2: AWS CLI Session Expiration & Local Host Dead-ends

* **What Happened:** When testing LocalStack from your laptop terminal, the AWS CLI repeatedly failed with `Your session has expired. Please reauthenticate using 'aws login'`. When we bypassed it with mock keys, it gave a `Could not connect to localhost` error.
* **How We Solved It:** 1.  We identified that your terminal had a leftover, expired AWS SSO active profile block messing with the local command. We bypassed it by injecting dummy inline environment variables (`AWS_ACCESS_KEY_ID=test`).
2.  We realized your terminal was pointing to `localhost:4566`, looking *inside your laptop* instead of across the network. We added a port-forward rule for `4566` to Apollo's interfaces file and routed the test over Tailscale using `--endpoint-url=http://100.81.86.51:4566`, resulting in a flawless S3 bucket verification.

### 💥 Roadblock 3: Broken Dashboard Links & `UNKNOWN` / API Error Badges

* **What Happened:** Homepage was showing an API connection error for Grafana, and hard `UNKNOWN` gray state flags for Portainer and Vaultwarden. The links were also mapped to the private `10.10.10.10` range, making them unclickable from your laptop browser.
* **How We Solved It:** 1.  We accessed Hestia's configuration files using `kitty vi services.yaml`.
2.  We swapped out all internal `10.10.10.x` references inside the clickable `href` parameters and replaced them with Apollo's Tailscale IP (`100.81.86.51`), making every button work instantly from your laptop browser.
3.  We stripped away the broken local Docker socket links and internal Grafana widgets, turning them into sleek, instantaneous, maintenance-free application launcher buttons while leaving the Prometheus target statistics widget completely green and active.
