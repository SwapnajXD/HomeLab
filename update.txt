# Athena Network Incident Postmortem

## Incident Date: 2026-06-21 → 2026-06-22

---

# Executive Summary

Between **21 June 2026** and **22 June 2026**, Athena appeared offline from the Tailscale network and became unreachable from Artemis.

Initial symptoms strongly suggested a Tailscale failure. However, deeper investigation revealed that Athena itself remained operational, local networking remained healthy, and the observed Tailscale failures were likely a downstream symptom of a temporary loss of Internet connectivity.

By the end of the investigation, Internet access, Tailscale connectivity, and SSH access had all recovered without requiring configuration changes, indicating a transient network interruption rather than a failure of Athena, Apollo, Proxmox, or Tailscale.

## Symptom

Every run of:


## Investigation


revealed:

```json
{
 "track": "Aap Jaisa Koi - From "Qurbani"",
 ...
```

---

## Root Cause

Song title contained quotes:

```text
"Qurbani"
```

which broke JSON.

The script was manually generating JSON:

```bash
cat <<EOF
{
 "track": "$TRACK"
}
EOF
```

Unsafe.

---

## Fix

Replaced manual JSON generation with:

```bash
jq -n
```

Example:

```bash
jq -n \
 --arg track "$TRACK" \
 '{
   track:$track
 }'
```

---

## Result

Proper escaping.

Example:

```json
{
  "track": "SPLINTER",
  "artist": "F3miii"
}
```

No more parse errors.

# 🚨 What Broke

## 1. Infinite / overlapping cron executions

### Symptom:

* Repeated logs like:

  * `LASTFM UPDATED`
  * multiple executions per minute
  * system spam / duplicate runs

### Cause:

* No concurrency control in cron jobs
* `fetch_lastfm.sh` triggering `fetch_media.sh`
* overlapping execution every minute

---

## 2. jq parsing crash in media pipeline

### Error:

```
jq: error: Cannot index string with string "name"
```

### Cause:

* GitHub API response sometimes returned:

  * error JSON
  * non-array response
  * rate-limit message
* script assumed `.[]` always valid array

---

## 3. Broken media.json output

### Output observed:

```json
{
  "mode": "wallpaper",
  "title": "",
  "url": "https://raw.githubusercontent.com/.../"
}
```

### Cause:

* `$WALLPAPER` became empty
* GitHub API rate-limited → no valid file list
* fallback logic missing

---

## 4. GitHub API rate limiting

### Error:

```json
{
  "message": "API rate limit exceeded"
}
```

### Cause:

* Unauthenticated GitHub API usage
* cron calling API too frequently (every minute)
* no caching layer

---

# 🛠️ Fixes Applied

## 1. Added `flock` to all cron jobs

### Fix date: 2026-06-26 ~10:20 UTC

### Change:

```cron
flock -n /tmp/fetch_lastfm.lock ...
flock -n /tmp/fetch_media.lock ...
```

### Result:

✔ Prevented overlapping executions
✔ Eliminated cron spam loops
✔ Stabilized system timing

---

## 2. Fixed LastFM script robustness

### Fix date: 2026-06-26 ~10:25 UTC

### Changes:

* Added safe JSON validation:

```bash
jq empty "$TMP"
```

* Added safe jq access:

```bash
.track[0]?.name
```

### Result:

✔ No more jq crashes
✔ Safe fallback JSON output
✔ Stable `lastfm.json` generation

---

## 3. Fixed media pipeline logic

### Fix date: 2026-06-26 ~10:30 UTC

### Changes:

* Split logic cleanly:

  * LastFM mode (priority)
  * Wallpaper fallback mode

* Added safe GitHub parsing:

```bash
try (.[] | select(...)) catch empty
```

* Added fallback wallpaper:

```bash
default.jpg
```

### Result:

✔ No empty URLs
✔ No broken JSON output
✔ Stable media switching system

---

## 4. Identified GitHub API rate limit issue

### Fix decision:

* confirmed as external constraint (not script bug)
* decided NOT to over-engineer caching yet

### Result:

✔ system continues to work when API resets
✔ fallback ensures UI never breaks

```javascript
olympusStarted = true;

buildOlympus();

setInterval(buildOlympus,10000);

}

if(document.readyState==="loading")
document.addEventListener("DOMContentLoaded",startOlympus);

else
startOlympus();
```

Result:

Widget loaded on both desktop and phone.

# Lessons Learned

### 1. Homepage is best treated as a dashboard, not an application framework.

While Homepage supports custom CSS and JavaScript, deeply modifying its DOM creates maintenance and compatibility issues, especially across devices and future updates.

### 2. Aggregate backend services only when they provide lasting value.

The Dashboard API successfully unified data from multiple sources, but its complexity wasn't justified after the custom widget was abandoned.

### 3. Test on multiple clients early.

The mobile-only rendering issue highlighted how different browsers and loading sequences can expose timing bugs that don't appear on desktop.

### 4. Keep the Git repository synchronized with live systems.

Capturing the latest configurations from Athena, Hestia, and Apollo before cleanup preserved the complete implementation history and provided a reliable rollback point.

### 5. Prefer simple, maintainable solutions.

The final decision to return Homepage to its standard configuration reduced operational complexity while preserving a stable and easy-to-maintain homelab.

```bash
    -o wlx002e2df0393b \
    -j MASQUERADE
```

Verified with:

```bash
iptables -t nat -L -n -v
```

Packets incremented correctly.

# Network Investigation

Verified:

### Forward chain

```
ACCEPT
```

### NAT

DNAT counters increasing.

### Ping

```

```

worked.

### Curl

```

```

worked.

### Docker

Confirmed Vaultwarden container:

```

```

Everything indicated networking was functioning correctly.

---

# Root Cause Discovery

Inspection showed:

```
ROCKET_TLS={
 certs=...
 key=...
}
```

Vaultwarden logs:

```
Rocket has launched from

https://0.0.0.0:80
```

This was the critical clue.

Vaultwarden was serving **HTTPS**, not HTTP.

---

# Why It Failed

Apollo forwarded TCP correctly.

However we were testing using

```
http://10.10.10.2:8080
```

Vaultwarden expected:

```
TLS ClientHello
```

Instead it received:

```
GET / HTTP/1.1
```

Vaultwarden logged:

```
tls handshake failed:
received corrupt message of type InvalidContentType
```

This error was entirely due to the client speaking HTTP to an HTTPS endpoint.

---

# Resolution

Changed the client to:

```
https://apollo:8080
```

or

```
curl -k https://10.10.10.2:8080
```

Vaultwarden immediately loaded successfully.

No networking changes were required.

# Lessons Learned

1. **Always verify packet counters before assuming NAT is broken.**

   * Increasing DNAT counters proved packets reached Hestia.

2. **A successful TCP connection does not guarantee the application protocol is correct.**

   * TCP connectivity was fine; the issue was HTTP vs HTTPS.

3. **Application logs are invaluable.**

   * The Vaultwarden log (`Rocket has launched from https://0.0.0.0:80`) immediately identified the protocol mismatch.

4. **Validate each network layer independently.**

   * Routing
   * Forwarding
   * NAT
   * Docker port publishing
   * Application protocol

5. **Don't assume a service on port 80 speaks HTTP.**

   * Vaultwarden was explicitly configured to serve HTTPS on container port 80 via `ROCKET_TLS`.
